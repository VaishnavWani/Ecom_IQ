The problem this pipeline exists to solve

Order data. Payment data. Shipment data. Return data. Four systems, zero shared view.

When a courier starts mishandling a category in one region, or a payment gateway degrades, the evidence is already there — just scattered across systems that were never built to talk to each other. Nobody joins them until someone manually goes looking.

What's actually running

Four stages. One continuous stream.

Not a diagram of an intended design — this is the pipeline as built and dockerized, verified end-to-end.

01 / INGEST

Kafka + Zookeeper

Python producer seeds 7 dimension topics once, then streams 7 fact-event topics continuously — one micro-batch pushed per second.

confluentinc/cp-kafka:7.5.0
02 / PROCESS

Spark Structured Streaming

14 concurrent streams, each parsed against an explicit schema and written via foreachBatch — Spark has no native streaming JDBC sink, so every micro-batch is flushed with the standard batch writer.

spark-sql-kafka-0-10 · 3.5.1
03 / STORE

PostgreSQL — star schema

7 conformed dimensions, 7 fact tables. Region, courier, category and payment status are all queryable in a single join — no cross-system export required.

Kimball fact constellation
04 / SERVE

FastAPI

A REST layer over the same Postgres tables — health check plus queryable endpoints, containerized alongside the rest of the stack, ready for a BI tool on top.

uvicorn · 0.0.0.0:8000
Live pipeline demo — synthetic event generator, not production traffic
The data model

14 tables. Every fact table shares its dimensions.

Order lines, inventory transactions and clickstream events all resolve back through the same SKU and warehouse dimensions — that's what makes a single cross-domain query possible.

Tracing a regional courier failure

The synthetic dataset that validates this pipeline generates real return and payment-failure signal — 4 couriers (Delhivery, BlueDart, EcomExpress, DTDC), 4 regions, 3 categories, and a built-in ~15% return rate per order line — so this query pattern is provable against live tables, not a mockup.

03

Manually joins them in a spreadsheet by order ID and timestamp.

04

Root cause — one courier, one category, one region — confirmed after days of continued mishandling.

After — one query against the star schema

Minutes, not days

01

fact_returns joins to fact_order_lines joins to dim_skus — return reasons broken down by category, live.

02

fact_shipments filtered by courier_name and region surfaces the exact courier/region pairing.

03

Spark's 5-second micro-batch trigger means the anomaly is in Postgres almost as soon as it happens.

04

Ops reroutes that courier for that category the same day the pattern starts.

Minutes
Detection lag — bounded by query time, not by someone remembering to look.
Who actually needs this

Three operators, three different blind spots

3PL / Warehouse

Which side of the chain broke?

Managing multiple clients' SKUs across regions — need to isolate whether a failure is courier-side, warehouse-side or product-side before pointing fingers.

D2C, self-fulfilled

Catch it before it compounds

A payment gateway degrading or a fraud spike costs more the longer it runs unnoticed — same event stream, same lag to close.

Marketplace

Trace it to the responsible party

Root-cause tracing across seller, SKU and region is how you know who to penalize or support — not a guess from aggregate metrics.
